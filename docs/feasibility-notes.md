# Feasibility notes — from "browser extension" to "on-phone automation"

This documents the analysis of the original idea (see the 16-page handoff PDF)
and why the project pivoted. Written Nov 2026.

## Origin

The PDF describes a **Chrome extension**: paste a Shopee link, see 4 values —
Original Price, Product Discount, Shop Voucher, Platform Voucher. It
recommends Manifest V3, includes starter code, and ends with an honest note
admitting the code was never verified.

## Verdict on the original extension plan

**The idea is feasible; the PDF's code is not.**

- **Product prices** (original + current) are reliably available on the page.
- **Shop vouchers** are usually visible on the product page.
- **Platform vouchers are inherently an estimate** — they are personalized
  (claimed vouchers, coins, loyalty tier) and often finalize at checkout.
  Any implementation can only show "best available".
- The PDF's sample code has three fatal flaws it even admits to:
  1. `popup.js` injects into the *currently active tab* and ignores the pasted link.
  2. Its CSS selectors (`.pq7Z2G` etc.) are invented; Shopee obfuscates and
     reshuffles class names every few months.
  3. Manifest V3 `chrome.webRequest` cannot read response bodies, so the
     "intercept the API" approach as written doesn't work.
- Shopee's product API (`/api/v4/pdp/get_pc`) has required anti-bot headers
  (`af-ac-enc-dat`, `sz-token`, CSRF + rotating hashes) since ~2023; those
  headers are generated by Shopee's own in-page JavaScript. Synthetic requests
  from your own code fail — commercial scrapers fall back to full browser
  automation. A working extension must instead **read data the logged-in page
  already loaded** (MAIN-world fetch/XHR hook + DOM fallback).

## Why automation won (the constraint)

**Price checking happens on a phone.** That rules out the desktop extension as
the primary deliverable:

- **Chrome for Android has no extension support** (still true in 2026).
- Extension-capable Android browsers exist — **Firefox for Android** (official
  add-ons), **Quetta**, **Vivaldi 8.2+**, **Yandex** — but they run **Shopee
  mobile web**, which shows fewer vouchers/promos than the app, and pushes
  features to the app. (Kiwi Browser, the old answer, shut down Jan 2025.)
- PC-driven phone automation (Appium / uiautomator2) is fully capable but
  violates the phone-only constraint.

**Chosen: AutoX.js accessibility automation reading the real Shopee app.**

| | Extension (desktop) | Extension (Android browser) | **AutoX.js automation** |
|---|---|---|---|
| Where it runs | PC browser | mobile web | **the Shopee app itself** |
| Voucher fidelity | logged-in web | partial web | **logged-in app, app-only promos** |
| Anti-bot exposure | must hook page load | must hook page load | **none (reads own screen)** |
| Maintenance | CSS/API churn | CSS/API churn | UI-text patterns |
| Constraints | PC needed | fewer vouchers than app | Android only |

The automation route also solves the PDF's two hardest problems (anti-bot and
personalized vouchers) at once: it reads the screen the app rendered for the
logged-in user, with no synthetic requests at all.

## Current architecture (`automation/shopee-price-check.js`)

```
floating panel (floaty overlay)
  ├─ "Go": parse link (input box / clipboard) → resolve short links (redirect)
  ├─ open https://shopee.ph/product/{shopId}/{itemId} via VIEW intent (deep-links into app)
  ├─ wait for Shopee package + price text (poll accessibility tree)
  ├─ (optional) one gentle scroll if vouchers are lazy-loaded
  ├─ heuristic extraction of the 4 parameters (text patterns + bounds)
  └─ display on panel + append to price_log.csv
```

Link parsing and formatting are pure functions, unit-tested under Node.js
(`automation/tests/test_pure_functions.js`). A **Dump UI** button saves the
full accessibility tree so broken heuristics can be re-tuned quickly after
Shopee app updates.

## Risks & rules

- **ToS gray area**: Shopee's terms prohibit automated access. Reading your own
  screen is passive and low-risk; auto-claiming vouchers / auto-checkout is the
  classic ban pattern. The script is deliberately **read-only**.
- **Maintenance**: extraction is heuristic; Shopee app updates can require
  re-tuning the regexes (Dump UI workflow exists for exactly this).
- **Vouchers are estimates**: values shown are page-visible offers for the
  logged-in account; the final discount depends on claiming and checkout.
- **Platform lock-in**: Android-only (iOS exposes no accessibility API for
  third-party apps and Safari extensions need a Mac).

## Rejected alternatives

- Server-side scraper — IP blocks, CAPTCHAs, needs backend, worst fidelity.
- Direct Shopee API calls — anti-bot headers make this unreliable.
- PC-driven Appium — violates the phone-only constraint.
- iPhone anything — no viable automation or extension route.
